Fixing the Laggy Camera Feed — Lazeez Restaurant DMSS / Dahua NVR

How we diagnosed and fixed Channel 9 streaming slow/choppy in the DMSS iPhone app, what each setting does, and the final recommended configuration. Includes the actual screenshots taken during the session.

Date: 22 Apr 2026 App: DMSS (iOS) + SmartPSS (macOS) NVR: DHI-NVR5232-4KS2 NVR SN: 7H04666PAZ5CA4E Problem camera: Channel 9 — DH-IPC-HDW2230T-AS-S2

TL;DR — what actually fixed it

The slow camera (Channel 9) was set to 4096 Kbps while a smooth camera on the same NVR ran fine at 2048 Kbps. The camera's link to the NVR couldn't sustain 4 Mbps cleanly. We dropped Channel 9's bitrate to match the smooth camera (2048 Kbps main / 512 Kbps sub) and that made it watchable. The codec swap (H.265 → H.264) we tried first was a red herring — bitrate, not codec, was the bottleneck.

Where to make the change: you can't do it in DMSS for cameras behind an NVR — use SmartPSS on a Mac/PC → add the NVR by SN (P2P) → Device CFG → Encode → Channel 9. Full walkthrough below.

1 · Background — why some feeds lag and others don't

On this setup all cameras are IP cameras wired (PoE) into a single NVR (Network Video Recorder — the box that records footage, powers the cameras over Ethernet, and streams everything to the DMSS app). DMSS connects to the NVR, and the NVR relays each camera.

Common reasons one feed is choppy while others are real-time:

  • Sub-stream vs main-stream: grid/multi-view uses each camera's low-res sub-stream; full-screen usually switches to the main-stream.
  • Per-camera encode settings: each channel has its own codec / frame rate / bitrate. A camera set too high for its link will stutter.
  • Codec: H.265 is ~50% more bandwidth-efficient than H.264 but heavier for the phone to decode. Older cameras are H.264-only.
  • Connection path: on home Wi-Fi DMSS talks to the NVR over LAN (fast); away from home it goes through Dahua's shared P2P relay (slower).
  • Physical link: a long/damaged PoE cable run can negotiate down to 10 Mbps half-duplex and starve the stream.

2 · Identifying the slow camera

In DMSS, the home screen lists device groups. The restaurant's NVR appears as "Lazeez Res" (also visible under another saved group earlier in the session as "Office N Home" — same physical NVR). Tapping a tile's ⋯ → Device Details shows that camera's model and serial.

Naming note "HDW2230T-AS-S2" — the AS suffix means it has an audio-input jack + alarm I/O; S2 is the hardware refresh. It supports both H.264 and H.265. A different, smooth camera on the same NVR (Channel 16, model IPC-HDBW2220R-VFS) was the comparison point that cracked the case — see §6.

3 · Why DMSS itself can't fix it

For cameras connected behind an NVR, DMSS strips out the encode settings. The per-camera ⋯ → Device Details screen only exposes AI, Image Adjustment (just WDR + Flip), and More (Audio Recording + Audio Noise Reduction). There is no codec / bitrate / frame-rate control here.

So: to change encode settings you go in through the NVR — easiest from a laptop using SmartPSS.

4 · Getting into the NVR with SmartPSS

SmartPSS is Dahua's desktop client (Windows/macOS). It can connect to the NVR over the same P2P link DMSS uses — no LAN access, no port forwarding, works from anywhere with internet.

6 · The fix — codec experiment, then the real cause

Attempt 1 — switch H.265 → H.264 (didn't fix it)

Channel 9 was on H.265 for both streams. We changed both Encode Type dropdowns to H.264 and saved. The Ref Stream range updated (512–5632 → 1792–6144 Kbps), confirming the change stuck — but the feed was still slow, including in the grid.

The clue — a smooth camera on the same NVR

A camera that played back smoothly (Channel 16, IPC-HDBW2220R-VFS) was running H.265 at 2048 Kbps main / 512 Kbps sub. Channel 9 was at 4096 / 1024. Same NVR, same P2P path, same phone — so the codec wasn't the bottleneck. Bitrate was. Channel 9's link couldn't sustain 4 Mbps.

The fix that worked In the Encode dialog for Channel 9, set Main Stream → Bit Stream: 4096 → 2048 Kbps and Sub Stream → Bit Stream: 1024 → 512 Kbps — matching the smooth camera. Save, force-quit DMSS, reopen. That made it watchable.

Codec, after the bitrate fix

With Channel 9 now identical to the smooth Channel 16 (H.265, 2048/512), any residual lag isn't codec or bitrate — it's physical (§9). Practical guidance:

  • If the link is the bottleneck (bandwidth-bound): H.265 wins — same quality, half the data.
  • If the phone struggles to decode (decode-bound): H.264 wins — much lighter to decode.
  • Going below ~1536 Kbps main / 384 Kbps sub starts showing compression blocks on motion — not worth it.
  • Lower bitrate doesn't increase frame rate; it just gives more headroom so the stream recovers faster after dropouts.

7 · Audio — making voices clearer

The muffled audio is the codec/sample rate plus the cheap on-board mic. Things that help, in order of effort:

  1. DMSS → Channel 9 → ⋯ → Device Details → More → turn ON "Audio Noise Reduction" (it was off — see screenshot in §3). Quick win for these mics.
  2. SmartPSS → Encode → Audio Setup: change Encode Mode from G.711A → AAC (or G.711Mu as fallback), and bump Audio Frequency 8k → 16k if offered. Some firmware only lists G.711A/G.711Mu/PCM — if so, try PCM (uncompressed; you have bitrate headroom now) and 16k.
  3. Hardware limit: the HDW2230T-AS-S2's built-in mic is a tiny surface-mount part inside the dome. No codec setting rescues that. The real upgrade: plug a ~$20 line-level pickup mic (e.g. Dahua HFW1009) into the camera's Audio Input jack, then switch the audio input source from Mic to Line-in in the camera's own settings.
Observed In this session, switching the codec didn't make the audio noticeably better — strongly pointing at the mic/firmware ceiling. The Audio Noise Reduction toggle + an external mic are the meaningful next steps.

9 · Still laggy? The physical-link checklist

If Channel 9 is still choppy at settings identical to a smooth camera, it's the hardware/cabling. From Device CFG → Camera → Remote Device you can see each camera's IP (all on Dahua's internal PoE subnet 192.168.18.x, meaning every camera is wired directly into the NVR's back PoE ports). Channel 9 is at 192.168.18.237. The Remote Device screen doesn't show link speed, so on-site:

  • Swap Channel 9's Ethernet to a different PoE port on the back of the NVR (the NVR re-assigns automatically).
  • Inspect the cable run — Cat5/5e over ~50 m, or a pinched/wet cable, causes packet loss and a 10 Mbps half-duplex negotiation.
  • Try the spare camera — a second HDW2230T-AS-S2 was discovered (un-added) at 192.168.18.239. If it streams fine on Channel 9's port, the camera itself is the fault.
  • Update the camera firmware — older HDW2230T-AS-S2 firmware had a known intermittent packet-burst bug.
  • Camera-direct override: some camera firmware ignores the NVR's encode override. On the LAN, add the camera by IP in SmartPSS (user admin, password in the private notes) and force the codec/bitrate in its own Encode page.
