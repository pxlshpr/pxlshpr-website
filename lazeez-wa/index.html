WhatsApp Order → Deposit → Receipt flow

Setup guide & runbook for Lazeez Gourmet · self-hosted on the Vultr box · last reviewed May 2026

What this builds: the customer still taps the existing Order on WhatsApp button on the menu site (which opens a pre-filled wa.me message to your number). The new bit: a small service on your Vultr server receives that message via the WhatsApp Cloud API, reads the Grand Total off it, and auto-replies from your number with a deposit request (≥ 50%). The customer sends back a transfer receipt photo; the server OCR-checks the amount and drops a ✅/⚠️ note into the same thread so the waitstaff sees the verdict at a glance.

Cost: free for the messages in this flow (customer always messages first → 24‑h service window → replies are $0). You pay only for the Vultr box you already have. Going outside the 24‑h window later (e.g. "your order's ready" next day) needs a paid utility template — fractions of a cent. Cost detail ↓

What the waitstaff see

One ordinary-looking WhatsApp thread per customer, in chronological order: order → deposit request → receipt photo → ✅/⚠️ verdict. Because the bot's messages and the verification note live in the same thread, a staffer opening it gets the whole story in three seconds: did they pay, how much, is it enough, anything fishy. They can type a normal reply from the shared inbox at any point (that pauses/overrides nothing — it's the same conversation).

Two ways to give them that inbox — pick one (detail in §6):

  • Meta's built-in Inbox in WhatsApp Manager (business.facebook.com → WhatsApp Manager → Inbox). Free, web-based, multi-user, basic. phase 1
  • Your own little dashboard on the Vultr box — a page that lists threads + messages + the ✅/⚠️ flags with colour. More work, full control, also free. phase 2 if needed

6 · Part C — Server-side receipt verification how far can we go

Short version: yes, the server can read the slip and sanity-check it — but treat it as an assistant that flags, never as proof of payment. A screenshot can be edited; OCR misreads blurry photos; every bank's slip looks different. The verdict goes to the staff, who still glance at it. If you want real, tamper-proof confirmation, the answer isn't OCR — it's taking the deposit through a payment gateway (see the box at the end).

What the check actually does (on each receipt image)

  1. OCR / vision extract the slip. Two practical options:
    • Tesseract on the box — free, offline, decent on clean BML/MIB slips, weaker on photos-of-screens.
    • A vision model (Claude, or a cloud OCR like Google Vision / AWS Textract) — far more robust on messy real-world photos, costs a few cents per image, needs an API key. Given volume, this is cheap and the better choice. You can even ask the model to return structured JSON: {amount, currency, payee_name, payee_account, datetime, reference, bank}.
  2. Validate against the order state:
    • Amount ≥ deposit required? (or ≥ remaining balance if they'd part-paid before)
    • Currency is MVR?
    • Payee name / account matches your account (fuzzy match — slips abbreviate names)?
    • Timestamp recent (within, say, the last 2 h)? An old slip = red flag.
    • Reference / transaction number not seen before in your state DB — stops someone re-sending one valid slip for two orders.
    • Did OCR actually find an amount at all? If confidence is low → don't auto-confirm, just flag "couldn't read — please check manually".
  3. Decide & act:
    • All green → mark order confirmed, reply ✅ to customer, internal note "✅ verified MVR x, ref #…".
    • Amount short → mark partially_paid, store the credit, reply asking for the balance, internal note ⚠️.
    • Anything else off (stale, wrong payee, dup ref, unreadable) → don't confirm, reply "a team member will check this", internal note ⚠️ with the reason.

How the flag reaches the waitstaff

The thread already shows the bot's ✅/⚠️ message. On top of that, write an internal-only note they can see in the inbox you choose:

  • Meta's WhatsApp Manager Inbox: no true "internal note" feature beyond assigning/labelling conversations. You can apply a label like ⚠️ payment-check or ✅ paid to the conversation via the API — that's visible in the Inbox and is enough to triage at a glance.
  • Your own dashboard: render the note as a coloured inline row (the dashed centre bubble in the mockup above) — richest option, and you control exactly what staff see (reason, OCR'd amount, confidence).

The robust alternative to receipt screenshots — payment links. If the deposit is collected via a Maldivian gateway (BML's payment gateway / MPOS, Ooredoo m‑Faisaa, Dhiraagu, Fahipay, or a regional one) instead of a manual transfer, the bot can send a pay link for the exact deposit amount, and the gateway calls your server back with a real, signed "paid MVR x, txn #…" webhook. No OCR, no fakes, instant confirmation. Downsides: gateway fees (~2–3%), a merchant account, and integration work. Worth it if order volume is meaningful. You can ship the OCR version first and bolt this on later — the WhatsApp plumbing is identical.

Caveats worth re-reading:
  • The API number leaves the app. Migrating your current order number means staff lose the WhatsApp app on it and must use the web inbox. Easiest to start with a fresh number and update WHATSAPP_PHONE on the menu site.
  • Business verification is a gate. Unverified = throttled and can't fully go live. Start it day one.
  • OCR is advisory. Never auto-confirm on a low-confidence read. The ⚠️ path must always exist. Edited screenshots are a thing — payment links are the real fix if fraud becomes a problem.
  • Webhook needs valid public HTTPS. No domain ⇒ no webhook. Critical path item.
  • Reply to webhooks fast (< a few seconds). Ack 200 immediately, do OCR/sending in the background, or Meta retries and you get duplicates. Dedupe on message id.
  • No history backfill. Your server only sees messages from go-live onward. Store everything as it arrives.
  • Token hygiene. The permanent system-user token is god-mode for messaging — env file mode 600, never in git, rotate if leaked.

9 · Reference code (Node/Express sketch)

Webhook verify + signature check + order parse + send reply 
// app.js — minimal sketch, not production-hardened
import express from "express";
import crypto from "crypto";

const {
  PORT = 8090, GRAPH_VERSION = "v21.0",
  WABA_PHONE_NUMBER_ID, WHATSAPP_TOKEN, APP_SECRET, VERIFY_TOKEN,
} = process.env;

const app = express();
// keep the raw body so we can verify the signature
app.use(express.json({ verify: (req, _res, buf) => { req.raw = buf; } }));

// 1) Verification handshake
app.get("/webhook", (req, res) => {
  if (req.query["hub.mode"] === "subscribe" &&
      req.query["hub.verify_token"] === VERIFY_TOKEN) {
    return res.status(200).type("text/plain").send(req.query["hub.challenge"]);
  }
  res.sendStatus(403);
});

// 2) Incoming events
app.post("/webhook", (req, res) => {
  const sig = req.get("x-hub-signature-256") || "";
  const expected = "sha256=" + crypto.createHmac("sha256", APP_SECRET)
                                      .update(req.raw).digest("hex");
  if (!crypto.timingSafeEqual(Buffer.from(sig), Buffer.from(expected)))
    return res.sendStatus(401);

  res.sendStatus(200);                 // ack FIRST
  setImmediate(() => handle(req.body).catch(console.error));   // then work
});

async function handle(body) {
  for (const entry of body.entry || []) {
    for (const ch of entry.changes || []) {
      const v = ch.value || {};
      for (const m of v.messages || []) {
        const from = m.from;                          // customer's number
        if (alreadySeen(m.id)) continue;              // dedupe Meta retries
        if (m.type === "text")  await onText(from, m.text.body);
        if (m.type === "image") await onImage(from, m.image.id);
      }
    }
  }
}

async function onText(from, text) {
  if (!text.startsWith("*Lazeez Gourmet - Order*")) {
    return; // not an order — stay quiet, or send a "we'll reply soon"
  }
  const mt = text.match(/Grand Total:\s*MVR\s*([\d,]+(?:\.\d+)?)/i);
  if (!mt) return reply(from, "Got your order — a team member will confirm shortly.");
  const total   = parseFloat(mt[1].replace(/,/g, ""));
  const deposit = Math.max(100, Math.ceil(total * 0.5));   // YOUR rule
  saveOrder(from, { total, deposit, status: "awaiting_receipt", paid: 0, refs: [] });
  await reply(from,
`Thanks for your order! 🙌 To confirm it we need a deposit of at least 50%.

*Deposit due: MVR ${deposit.toFixed(2)}*  (of MVR ${total.toFixed(2)})

Transfer to:
• Bank of Maldives — Lazeez Gourmet Pvt Ltd
• Acct 7770000XXXXXX
• Reference: your name

Then send a photo of the transfer slip here and we'll confirm. Order held 20 min.`);
}

async function onImage(from, mediaId) {
  const order = getOrder(from);
  if (!order) return reply(from, "Send your order first, then the transfer slip 🙏");
  const buf  = await downloadMedia(mediaId);
  const slip = await ocrReceipt(buf);   // {amount,currency,payee,datetime,reference,confidence}

  const problems = [];
  if (!slip || slip.confidence < 0.6)             problems.push("couldn't read the slip clearly");
  if (slip && slip.currency && slip.currency !== "MVR") problems.push(`currency ${slip.currency}`);
  if (slip && !payeeMatches(slip.payee))           problems.push("payee doesn't match our account");
  if (slip && tooOld(slip.datetime))              problems.push("slip is not recent");
  if (slip && order.refs.includes(slip.reference)) problems.push("this slip was used before");

  const amount = slip?.amount ?? 0;
  const need   = order.deposit - order.paid;

  if (problems.length) {
    note(from, "⚠️ " + problems.join("; ") + ` · read amount MVR ${amount}`);
    return reply(from, "Thanks — a team member will check this slip and get back to you.");
  }
  if (amount + 1e-6 < need) {
    order.paid += amount; order.refs.push(slip.reference); order.status = "partially_paid"; saveOrder(from, order);
    note(from, `⚠️ part payment MVR ${amount}, still need MVR ${(order.deposit - order.paid).toFixed(2)}`);
    return reply(from, `Got MVR ${amount.toFixed(2)} — short by MVR ${(order.deposit - order.paid).toFixed(2)}. Please send the balance + the new slip.`);
  }
  order.paid += amount; order.refs.push(slip.reference); order.status = "confirmed"; saveOrder(from, order);
  setLabel(from, "✅ paid");
  note(from, `✅ verified MVR ${amount} · ref ${slip.reference}`);
  await reply(from, `✅ Payment received — MVR ${amount.toFixed(2)}. Your order is confirmed! See you soon. 🍔`);
}

// --- Graph API helpers ---
async function reply(to, body) {
  await fetch(`https://graph.facebook.com/${GRAPH_VERSION}/${WABA_PHONE_NUMBER_ID}/messages`, {
    method: "POST",
    headers: { Authorization: `Bearer ${WHATSAPP_TOKEN}`, "Content-Type": "application/json" },
    body: JSON.stringify({ messaging_product: "whatsapp", to, type: "text", text: { body } }),
  });
}
async function downloadMedia(mediaId) {
  const meta = await (await fetch(`https://graph.facebook.com/${GRAPH_VERSION}/${mediaId}`,
                 { headers: { Authorization: `Bearer ${WHATSAPP_TOKEN}` } })).json();
  const res  = await fetch(meta.url, { headers: { Authorization: `Bearer ${WHATSAPP_TOKEN}` } });
  return Buffer.from(await res.arrayBuffer());
}

10 · Suggested order of operations

  1. Get a number + a (sub)domain. Start Meta business verification. days, runs in background
  2. Create the Meta app + WhatsApp product, play with the test number + temp token.
  3. Stand up the Vultr service against the test number: webhook verify, signature check, parse order, send deposit reply. Smoke test.
  4. Add image handling + OCR + the ✅/⚠️ logic + state DB. Smoke test with photos.
  5. Add the real phone number, get the display name approved, generate the permanent token, point the webhook at prod, flip the app to Live.
  6. Wire up the staff inbox (Meta Inbox first) + brief the staff on the ✅/⚠️ convention.
  7. Update WHATSAPP_PHONE on the menu site to the new API number. Soft-launch, watch the threads for a few days.
  8. Later, if warranted: own dashboard, payment-link deposits, "order ready" utility template.
